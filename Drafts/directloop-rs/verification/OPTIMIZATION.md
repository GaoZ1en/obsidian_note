# 精确消元优化记录

2026-10-16。本轮在已有 Rust 实现上继续优化，保持 `lambda=7/5` 的有理数秩计算。原 notebook 未修改。

## 实测结果

Apple M5，10 核 CPU、16 GB 内存，macOS 26.5.1；4 个生成线程和至多两个消元线程。均从空目录计算到 `L=22`，包含进程启动、各层计算、JSON 输出和正常断点保存，不含编译。

| 版本或配置 | 次数 | 总耗时 | 峰值 RSS |
|---|---:|---:|---:|
| 优化前 Rust | 1 | 56.605 s | 1.582 GiB |
| 只做缓存与消元缓冲区优化 | 1 | 51.003 s | 1.406 GiB |
| 最终默认：批次 2048、短行优先、短主元 | 3 | 中位数 **31.629 s** | 1.572–1.788 GiB |
| 较低内存：批次 256、主元列升序、短主元 | 1 | **37.149 s** | **1.424 GiB** |

最终默认三次为 31.2688、31.6294、31.6329 秒，比本轮优化前的 Rust 单次基准缩短约 **44.1%**，约为其 **1.79 倍速度**。不是相对 Mathematica 再增加 30 倍。较小的 `L=18` 最终三次中位数为 0.3324 秒，早期 Rust 为 0.3395 秒，差异很小。

默认配置优先选取本机测得的速度收益，**总峰值 RSS 没有稳定下降**。虽然长期主元行已收紧容量，更大的批次、分配器保留内存和不同消元顺序仍影响进程峰值。需要较低内存时可使用表中第二种最终配置。RSS、macOS physical footprint 和整个系统的内存需求不是同一个指标；这些数据不能直接推算 Linux 上的峰值。

最终默认的累计 AllE 消元操作次数从 45,546,299 减到 18,136,537；SDE 从 16,557,140 减到 14,331,178。最大中间行项数从 2729 变为 2999，因此没有声称每条中间行都变短。

主要原始记录：`optimization-baseline-L22.json`、`optimization-alloc-cache-L22.json`、`optimization-final-L22.json`、`optimization-final-low-memory-L22.json`。报告均记录可执行文件 SHA-256、参数、逐层计数和耗时。

## 保留的改动

1. 消元在两个缓冲区之间交换数据，复用临时分配；长期保存的主元行收紧容量。超过 65536 项的临时容量不保留在复用缓存中，方程本身不受这个阈值限制。
2. 可选的主元缓存化简如果产生超过 128 项的行，保留原主元，并暂缓重复尝试，直到新增约 4096 个主元。必要的主元消元照常进行；不会据此判定行相关或丢弃非零项。
3. 相同主元列出现更短的行时，交换主元，把旧行继续消元。批内先处理较短的行，以改善后续使用的主元。
4. 已排序并合并的 SDE 系数直接构造精确整数行；单列主元用删除该列并精确归一化的路径处理。溢出后仍完整回退至宽整数或 BigInt，不使用浮点或模素数近似。
5. 路径在栈数组中解码，SDE 系数原地合并，TrE 直接写入批次缓冲区，并保留逐 loop 的原地去重。早期试验曾把去重全部推迟到批末，导致工作内存增大，没有保留该方案。

主元交换、消元及非零比例归一化保持有理数行空间。短主元策略仍按最大的非零列向下消元；新独立余项送入 AllE，已相关的输入不重复送入。缓存和缓冲区不属于数学状态，不写入 checkpoint。

## 顺序与批次试验

比较了输入顺序、短行优先、主元列升序、主元列降序，分别组合保留首个主元或优先短主元，共八种设置；全部运行到 `L=22`，各长度计数一致。主元列降序与短主元的一个组合反而用了约 73 秒，因此没有将其选为默认。完整结果见 `optimization-orders-L20.json`、`optimization-orders-L22.json`。

继续比较批次 256、2048、8192、32768。最终候选在 2048 时约 32 秒、32768 时也约 32 秒，但后者单次峰值 RSS 约 1.95 GiB；8192 的候选约 37.5 秒、2.16 GiB。没有把更大的批次视为自动更好。相关结果见 `optimization-compact-batch-*-L22.json`。

这些是有限实测，未证明全局最优，也没有证明在 `L=24` 或另一台机器上有相同的相对收益。

## 正确性与兼容性

**Verified:**

- 13 项 release 测试通过，包括精确消元、单列快速路径与一般大整数消元对照、极端系数与溢出回退、失败化简缓存、八种顺序组合的小长度计数、线程异常传播和断点续算。
- `L=4,6,...,16` 的完整基、seed、每个 SDE 的系数和规范化 TrE 记录，再次与原 Mathematica 数据逐项一致；1000 条随机路径规范化一致。
- 42 个独立 Mathematica `MatrixRank` 案例分别检查两种主元策略，并检查将两个子族的独立余项送入联合秩后的结果。
- 所有成功的性能试跑均检查从 4 到目标长度的每一层四项计数。`L<=22` 与既有对照表一致；不以计时成功代替数值验证。
- `L=18` 使用 1、4、16 个生成线程，批次 2048、256、17，以及串行/并行消元，计数一致；固定批次时操作次数一致。见 `thread-checks-optimized.json`。
- 从优化前的 `L=20` checkpoint 续算到 22，各层计数一致。该次约 65.1 秒，说明旧主元表会影响新策略的速度，不能拿续算计时代表新策略从零运行的性能。见 `checkpoint-compatibility-optimized.json`。
- `cargo clippy --all-targets --locked -- -D warnings` 通过。

**Assumptions:** 固定原路径等价关系、TrE 相对位置、常数列和 `lambda=7/5`；支持偶数长度 4 到 24。所有计算保持精确有理数行空间。

**Not verified:** 没有在 i9-14900HX / Linux 上运行；Linux 资源监测分支也尚未在目标机器实测。本次 `L=24` 完成了 SDE，但 TrE 和 AllE 未算完，且 `L=24` 没有独立 Mathematica 对照值。以上检查不证明原 notebook 的物理推导，也不覆盖其它耦合或长度。

## 优化版 L=24 资源试跑

使用最终默认算法、4 个生成线程，从空目录开始，设置 8 GiB 进程内存停止线、1.5 GiB 系统 swap 增长停止线及 900 秒试跑时限。实际在 **750.03 秒（12 分 30 秒）**时先触发进程内存停止线，未触发时间停止线。

| 项目 | 本次结果 |
|---|---:|
| L=24 新增 loop 基数 | 9,053,008 |
| 加上较短长度后的累计 loop 基数 | 10,427,422 |
| L=24 的 SDE 阶段耗时 | **604.981 s** |
| SDE 完成后的累计秩 | **6,903,264** |
| 最后一条 TrE 进度 | 975 / 4421 个批次 |
| 当时的累计 TrE 秩（非最终） | 1,243,918 |
| 峰值 RSS | 4.244 GiB |
| 最高采样 physical footprint | **8.080 GiB** |
| 最后完整保存的长度 | 22 |

每两秒采样，因此停止时指标可能略高于 8 GiB。上表的 `L=24` 数字来自这次 Rust 实算，尚无独立参考；**没有得到完整的 TrE/AllE 秩，也没有测到完整运行的总时间和最终峰值内存**。975/4421 是输入批次进度，不代表已完成同样比例的计算时间。

相近的 SDE 输入进度可作有限对照：初版处理约 1328 万条非零 SDE 行时，该层已用 609 秒；新版的相邻日志为 1299.6 万行 / 347.9 秒和 1329.7 万行 / 353.1 秒。日志并非严格同一输入点，但显示这一段的明显提速。初版试跑随后因系统 swap 增长停止，SDE 未完成；新版则完成全部 SDE 并进入 TrE。两次停止原因和最终进度不同，不能直接用 670 秒与 750 秒比较速度。

当前剩余的资源瓶颈出现在 TrE/AllE 阶段。8 GiB 停止线下未跑完，并不能确定 64 GB 机器上的最终需求。此前给出的小时级估算仍只能用于粗略排期。

原始记录为 `resources-m5-L24-optimized.json` 和 `resources-m5-L24-optimized-progress.log`。报告中 `levels` 只列已完整完成的长度；`incomplete_level_progress` 单独标记这次未完成的 24 层。完整 `L=22` checkpoint 保留在本机 `runs/measured24-optimized/checkpoint.bin`；程序仍按完成长度保存，中断的 24 层需重算。

## 运行设置

默认速度配置：

```sh
./run.sh --max-length 24 --threads 16 --output runs/L24-optimized
```

较低内存配置：

```sh
./run.sh --max-length 24 --threads 16 --batch-size 256 --row-order pivot-asc --pivot-strategy short --output runs/L24-lower-memory
```

64 GB 以上 Linux 的带监测试跑（先构建 release）：

```sh
python3 verification/measure_resources.py --max-length 24 --threads 16 --memory-limit-gib 48 --run-dir runs/L24-measured --report verification/resources-linux-L24.json
```

48 GiB 是进程 RSS 加其交换页的采样停止线，不是已证明足够的最终需求或严格内存配额。可按需要加 `--max-seconds` 设置试跑时长。为了比较新旧策略，优先从空目录开始。
